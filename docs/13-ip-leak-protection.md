# 13 · 真实 IP 泄漏防护

## 起因

用户用住宅代理访问 Claude。某天账号被 Anthropic 限制（`claude.ai/restricted`，
提示 *Your account is on hold*）。

排查代理侧日志后发现**确实存在真实 IP 暴露窗口** —— 中国不在 Anthropic 的
支持地区，**一次带真实中国 IP 的请求就足够触发风控**。

> 这不是"代理不好用"的问题，而是**代理短暂不可用时会把真实 IP 交出去**。
> 对普通浏览无所谓，对 Claude / ChatGPT 这类强风控服务是致命的。

## 泄漏是怎么发生的

### 场景 1：合盖休眠 → 唤醒（最主要）

```
合盖 -> 'Clamshell Sleep' -> Wi-Fi 关闭, utun 接口被系统撤掉
开盖 -> 唤醒, Wi-Fi 立刻重连, 但 TUN 要 ~30 秒才重建
     -> ★ 这段窗口里所有应用都是直连 ★
```

实测证据（2026-10-12）：

```
23:34:21  唤醒
23:34:52  收到退出信号, 撤掉 TUN      <- 31 秒之后才处理
23:34:53  TUN 已启动
```

**那 31 秒就是 `dnsguard` 的 30 秒轮询周期。**

根因：`run-tun.sh` 判断"代理是否就绪"**只看 10808 端口**。休眠时 xray 只是被
挂起、socket 还在，守护就以为一切正常，**不去重建已经被系统撤掉的 TUN 接口**。

实测这台机器 **2 天内休眠/唤醒 17 次**，每次都有这个窗口。

**注意 `caffeinate` 挡不住合盖**：实测 `caffeinate -d -i -s` 跑了 2 天 17 小时，
合盖照样进入 `Clamshell Sleep`。

### 场景 2：代理进程死亡 / 端口失效

xray 崩溃、节点故障、v2rayN 内部错误 —— 只要 10808 不再监听，旧逻辑立刻
`stop_tun`，**路由恢复直连**，境外流量就带着真实 IP 出去了。

## 防护一：合盖不休眠

`pmset` 的 `disablesleep` 是隐藏设置，它阻止**包括合盖在内**的所有睡眠：

```bash
sudo pmset -a disablesleep 1
```

该值写在 `/Library/Preferences/com.apple.PowerManagement.plist` 里，**重启保持** ——
所以"开机自启"天然满足。

`daemon/sleep-guard.sh` + LaunchDaemon 做两件事：

1. **开机自检** —— 系统大版本升级 / 重置 NVRAM 可能清掉它，每次开机确认
2. **过热保护** —— 合盖且无输入超过阈值（默认 40 分钟）时主动放开睡眠。
   `disablesleep` 连合盖睡眠一起挡掉，装包里会持续发热，**严重时可能损坏机器**

阈值可调：

```bash
echo 2400 > ~/Library/Application\ Support/v2rayN/no-sleep-timeout   # 秒
```

配套脚本 `scripts/no-sleep.sh {on|off|status}`。

**实测（2026-10-13，合盖 8 分钟）**：

```
23:17:11  闭  1  有  在  63641  48.47.17.149  17    ← 合盖开始
23:20:22  闭  1  有  在  63641  48.47.17.149  17
23:24:59  闭  1  有  在  63641  48.47.17.149  17    ← 合盖结束
23:25:10  开  1  有  在  63641  48.47.17.149  17    ← 开盖
```

| 观察项 | 结果 |
|---|---|
| 休眠计数 | 17 → 17（没睡）✓ |
| sing-box pid | 63641 → 63641（TUN 一次都没重建）✓ |
| 出口 IP | 8 分钟 48 次采样全是 `48.47.17.149`（零泄漏）✓ |

**最有说服力的是出口 IP 那一列** —— 它直接证明没有任何一秒钟走的是直连。

## 防护二：kill-switch

原理：**代理不可用时，不要撤 TUN**。

```
代理掉线 + 保持 TUN:
  国内流量 -> direct 出口 -> 正常 ✓
  国外流量 -> proxy 出口 -> 10808 已死 -> 连接失败 ✓
  ★ 任何流量都不会绕出去, 真实 IP 永远不暴露 ★
```

**为什么不会死锁**：`sing-box.json` 里有 `"auto_detect_interface": true`，
sing-box 的 `direct` 出口会自动绑定物理网卡、不经过 TUN。所以 xray 要连节点时
走的是 `direct` 出口，能正常连出去 —— 节点恢复后自动接上。

### 关键设计：区分两种"代理掉线"

| 情况 | 判据 | 行为 |
|---|---|---|
| **代理暂时不可用** | v2rayN 进程还在 | **保持 TUN** —— 国外失败但绝不泄漏 ✓ |
| **用户主动退出** | v2rayN 进程已退出 | **撤掉 TUN** —— 干净退出，不留痕迹 ✓ |

这样"**任何意外都不漏真实 IP**"和"**退出即干净**"两个需求同时满足，不冲突。

代码就在 `run-tun.sh` 主循环里，判据是 `v2rayn_alive()`。

### 实测

**场景 A —— v2rayN 还在，代理端口死掉**（`kill -9 xray`）：

```
v2rayN 进程    还在 ✓
10808          已死
TUN            ★ 仍然存在 ✓
sing-box pid   93451 = 基线, 从未重建 ✓

国内 baidu     HTTP 200 ✓      <- 国内照常可用, 没被卡死
国外 google    HTTP 000        <- 失败
出口 IP        取不到 ✓        <- ★ 没有泄漏真实 IP ★
```

守护日志：

```
23:31:08 代理端口 10808 已下线, 但 v2rayN 仍在运行
         -> 保持 TUN (kill-switch: 国外连接会失败而非泄漏真实 IP)
```

**场景 B —— 退出 v2rayN**：

```
23:32:05 v2rayN 已退出, 撤掉 TUN (干净退出)
23:32:06 TUN 已停止 sing-box pid=93451
```

重开 v2rayN → 8 秒内 TUN 恢复 → 出口 IP 回到 `48.47.17.149` ✓

### 逃生舱

需要"代理不在了也保持 TUN"（比如长时间只出国内流量）时：

```bash
touch ~/Library/Application\ Support/v2rayN/killswitch-always
```

## 遗留问题

**v2rayN 不会自己重启 xray。** 实测把它 `kill -9` 之后，10808 一直不恢复，
国外访问持续不可用（虽然不泄漏）。这是 v2rayN 自身的行为，不在本项目的控制范围。

如果要更强的可用性，需要在守护里加"检测 xray 进程死亡并重启 v2rayN"的逻辑 ——
但那样又会引入"擅自操作 v2rayN"的风险，需要权衡。

## 教训

1. **"代理断了就恢复直连"是一个危险的默认值。** 它的出发点是"不让用户断网"，
   但对强风控服务，代价是把真实 IP 交出去。**对这类用户，默认应该是阻断而不是放行。**
2. **只探测端口不足以判断代理健康。** 休眠时进程还在、socket 还在，但网络栈已经
   被系统拆了。判断依据必须包含"接口是否真的存在"。
3. **轮询周期直接等于泄漏窗口。** 30 秒轮询 = 30 秒暴露。事件驱动（唤醒通知）
   比轮询好得多。
4. **用户的体感描述再次指向了真因。** 用户说"我合盖会断吗" —— 这个直觉比我
   一开始怀疑的"我测试时制造的窗口"更接近事实：真实使用中合盖/唤醒才是高频场景。
