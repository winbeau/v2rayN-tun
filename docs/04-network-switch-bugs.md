# 04 · 网络切换引发的两个真实 bug

> **一句话**：长驻进程「启动时探测一次」= 定时炸弹；`stop_tun` 里的 kickstart 会造成无限重建。

这是整个项目里**最难查、也最有价值**的一段。两个 bug 都会在网络切换后出现，症状却完全不同。

---

## Bug A：DNS 回落到 on-link 地址

### 现象
切网后（或路由器续租），`google.com` 解析到 Twitter 的 IP 段，浏览器行为异常。

### 根因
手动设置的公网 DNS 在多数情况下能持久保存，但换网/续租/某些网络工具重置配置时，会回落到 **DHCP/RA 下发的 on-link 地址**（如网关 `10.20.30.55`、IPv6 DNS）。

on-link 的 DNS 走链路直连、**不进 TUN** → 绕过 sing-box 的 DNS 劫持 → 返回污染结果。

### 解决：判定用因果关系，而非白名单比对
`daemon/dnsguard.sh` 只看一个事实：**主解析器实际使用的 DNS 是否全部为公网地址**。

```
含 on-link / 私有 / 链路本地 → 会绕过 TUN，改回公网 DNS
完全没有 DNS                → 解析已失效，一并修好
全部是公网地址               → 会走默认路由进 TUN 被劫持，放行
```

这样**不会和用户自定义的公网 DNS 打架**（若写成"必须是 223.5.5.5"就会）。

只统计「默认解析器」和「绑定主接口的解析器」，忽略其他接口（iCloud 私密代理、VPN 的 utun），因此不会误伤 VPN 自己的 DNS。

### 触发方式
launchd `WatchPaths`（网络配置变化即时响应）+ `StartInterval 30` 兜底。

**实测：清空 DNS 后第 3 秒被自动修复** —— 3 秒说明 WatchPaths 生效，30 秒轮询只是兜底。

## Bug B：sing-box 出站绑定停留在旧地址 ⭐

### 现象
切网后**所有直连出站失败**。表现五花八门，让人误判方向：

- 微信发消息转圈、截图发不出去
- DSH 报 `TRANSPORT` 错误并反复重试
- 部分国内网站打不开

### 弯路（重要）

1. **归因于"用户切热点"** —— 方向对了一半，机制完全错。当时以为是切换瞬间的抖动，没意识到**故障会持续存在**。
2. **怀疑 DNS / 路由 / 代理规则** —— 全部排除（路由判定正确、DNS 干净、无残留路由）。
3. **一度确认"绑定是正确的"就结案** —— 后来才明白：我测的那一刻网络刚切换完、守护已重启，所以看到的是好的。**没在故障发生时取数**。

### 真正根因

sing-box 在**启动时**检测网络接口并确定出站绑定，之后网络怎么变它都不知道。旧地址消失后它仍用它发包：

```
ERROR write udp 10.20.30.160:56026->119.29.29.29:53:
      write: can't assign requested address
```

当时 en0 已经是 `192.168.1.25`，而 sing-box 仍在用 `10.20.30.160`。

### 关键转折：用户的一句话

> "是不是你网络切换时候没有切换干净"

这句话把方向直接拨正。此前我一直在查"为什么慢"，而实际是"**为什么一直坏着**"。

### 解决

`dnsguard.sh` 增加：**记录 en0 地址，变化则重启 TUN**，让 sing-box 重新绑定。

- 60 秒防抖，避免网络抖动导致反复重建
- 健康时完全静默，不误触发（已验证）

### 实测验证（真实切换，非模拟）

```
05:13:04  sing-box: dial tcp 198.51.100.20:443: no route to internet   ← 切网
05:13:15  网络守护: 网络地址变化 192.168.1.25 -> 10.20.30.160, 重启 TUN
05:13:20  TUN 已重建, sing-box 绑定 = 10.20.30.160 = en0 ✓
```

**11 秒自动恢复。** 修复前这种情况会让 sing-box 一直绑着失效地址，直到手动重启。

---

## 教训

1. **"启动时探测一次"的常驻进程 = 定时炸弹。** 环境会变，进程必须能感知并重新绑定。
2. **故障是间歇的时候，必须在故障发生时取数**，事后测到的"正常"会误导你结案。
3. **用户的现象描述比我的推断更可靠。** 我说过两次"已排除"，都是错的；用户的两次直觉都是对的。
4. 两个 bug 同源（网络变化后没切换干净），但一个影响 DNS、一个影响出站绑定 —— **排查时不要假设"同一个根因只产生一种症状"**。
