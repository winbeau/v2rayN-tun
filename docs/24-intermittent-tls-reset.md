# 24 · TLS 握手被间歇性重置

> **一句话**：RST 在 8–10 ms 到达、而到节点 RTT 有 190 ms —— 服务器来不及回话，是在路上被掐的；而这种掐断会自己恢复。

## 症状

某个时刻开始，所有到代理节点的 TLS 握手都失败：

```
TCP 建连          ✓ 通（189–200 ms）
静置 3 秒         ✓ 不断
发明文 HTTP       ✓ 收到 14 字节回包
发 TLS ClientHello  ✗ 8–10 ms 后 RST
换任意 SNI        ✗ 一样 RST
连续 6 次         ✗ 6/6 全 RST
```

**看起来像"节点挂了"，但节点其实是好的** —— 从境外跳板机对同一 IP:端口做 TLS
握手，`CONNECTION ESTABLISHED` / TLSv1.3 全程正常。

## 怎么判断责任方

三个数字就能定死：

| 观测量 | 值 | 说明 |
|---|---|---|
| 到节点的 RTT | **190 ms** | TCP 建连耗时 |
| RST 到达时间 | **8–10 ms** | 从发出 ClientHello 到收到 RST |
| 明文 HTTP | **有回包** | 说明 TCP 通路是好的 |

**RST 比 RTT 快 20 倍 → 不可能是服务器发的** ✓
**TCP 通、明文通、只有 TLS 被断 → 是中间设备在做 DPI** ✓
**换 SNI 不影响 → 不是按域名封，是按"TLS 握手"这个行为封** ✓

## 真相：会自己恢复

故障发生后约 30 分钟，**同一个网络、同一个 IP、同一个网关、同一个 EasyConnect**
再测：

```
154.17.29.33:4561    8/8 成功
154.17.27.236:4561   7/8 成功
```

**网络配置一个字节都没动。**

## 这次踩的四个误判

排障过程中先后得出过四个错误结论，都被后来的数据推翻：

| # | 当时的判断 | 为什么错 |
|---|---|---|
| 1 | 「节点挂了 / 服务商问题」 | 从境外跳板机测同一 IP:端口，TLS 全程正常 |
| 2 | 「订阅过期了，要重新导入」 | 逐字段比对 uuid / 公钥 / short_id / 端口 / SNI，**一个都没变** |
| 3 | 「EasyConnect 引起的」 | 换到手机热点后恢复，但 EasyConnect 全程没动、utun5 路由也没变 |
| 4 | 「是新疆电信宽带在封」 | 换回校园网后同样恢复，**故障和正常时 en0 / 网关完全相同** |

**第 3 和第 4 条特别有迷惑性**，因为两次"恢复"都恰好发生在换了网络之后 ——
但真实原因是**时间过去了**，不是网络换了。

## 最可能的原因

**路由器 / 运营商的上网行为管理（DPI）在短时间大量 TLS 握手时触发临时封禁，
过一段时间自动解除。**

排障时为了定位，十几分钟里连续测了几十次 TLS 握手 —— 很可能正是这个触发了阈值。

## 教训

### ① 间歇性故障要在【两个时刻】取数，不止一个

[原则 2](../AGENTS.md) 说「间歇性故障必须在故障发生时取数」。这次要补一句：
**恢复之后还要再取一次**，并且**逐项对比两次的环境**。

这次如果能早点做「故障时 en0 = X」和「恢复时 en0 = X」的对比，
就能立刻排除「网络换了」这个假设，少走两小时弯路。

### ② 故障中不要仓促改配置

这次差点在故障窗口里：重新导入订阅、换节点、改 DNS、改路由。
**全都是白费** —— 问题不在配置。

**先证明「是不是外部在变」**（见 [20](20-node-params-changed.md)），
**再动手改自己的东西**。

### ③ 排障手段本身可能是触发器

密集重试（十几分钟几十次 TLS 握并）会触发 DPI 阈值。
**排障时把间隔拉到 30 秒以上**，既避免自己触发，也让数据更干净。

### ④ 排除法要有「同一时刻」的对照

「换热点好了」不能证明是宽带的问题 —— 中间还过了 20 分钟。
**要做对照，必须在同一时刻、只改一个变量。**

## 复发时怎么处理

```
1. 先等 10–30 分钟，别改任何配置
2. 再测一次同样的东西
3. 恢复了 -> 就是 DPI 临时封禁，记下时间点
4. 没恢复 -> 才轮到怀疑节点 / 订阅 / 配置
```

**判定用的命令**（三层分开测，缺一不可）：

```bash
# ① TCP 层
nc -z -G 3 -w 3 <节点IP> 4561 && echo "TCP 通"

# ② TLS 层（关键：看是不是 RST）
echo | timeout 6 openssl s_client -connect <节点IP>:4561 \
  -servername www.cooper.edu -brief 2>&1 | head -2

# ③ 对照：从境外跳板机测同一 IP:端口
ssh huawei1 'echo | timeout 6 openssl s_client -connect <节点IP>:4561 \
  -servername www.cooper.edu -brief 2>&1 | head -2'
```

**② 失败而 ③ 成功 → 是路上的设备** ✓
**② ③ 都失败 → 才是节点的问题** ✓
