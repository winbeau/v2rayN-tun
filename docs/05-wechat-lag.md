# 05 · 微信卡顿排查（三次错误结论）

> **一句话**：**空日志 ≠ 没有事件** —— 三次错误结论都源于此。

**现象**：发消息要"略微转一下"才发出；截图一直发不出去。

最终根因与 [04 · Bug B](04-network-switch-bugs.md) 相同（sing-box 出站绑定失效）。本文记录的是**三次把方向带偏的错误判断**，因为它们的教训比结论更有价值。


> **⚠️ 现状已变（2026-10-15）**：本文结论"微信没有被代理"是彼时的情况。
> 后来国内方向整体改走日本节点，微信被卷了进去，**发不出图片/文件** ——
> 因为腾讯的网络对境外 IP 一律拒绝。已把 16 个腾讯/微信域名加进直连例外，
> 详见 [18](18-risk-register.md)。

---

## 错误结论 1：用"日志为空"推断"没走代理"

**推理**：xray 日志里没有微信的连接 → 微信没被代理 → 排除代理因素。

**为什么错**：xray 的 `loglevel` 是 `warning`，而**连接日志需要 `info`**。日志一直是空的，我却把它当成了证据。

**验证方法**：人为制造一条必经代理的流量，看日志是否新增。

```bash
B=$(wc -l < <logfile>)
curl -x http://127.0.0.1:10808 https://www.google.com/generate_204
A=$(wc -l < <logfile>); echo "新增 $((A-B)) 行"    # 0 行 = 日志根本没开
```

**教训**：**下结论前先验证观测手段本身是否有效。** 空日志有两种含义：「没有事件」和「没有在记」。

---

## 错误结论 2：用"没有长连接"推断"每次要重建"

**推理**：微信当前只有 2 条外部连接，没有常驻长连接 → 每次发消息都要重新建连 → 所以慢。

**为什么错**：只采样了一个瞬间。延长监控到 90 秒后发现**长连接一直稳定存活**：

```
t=00s ~ t=90s   14.116.242.250:8080 与 183.47.121.90:80 始终存在
```

**教训**：涉及"是否存在/是否稳定"的判断，**采样窗口必须长于该现象的特征周期**。单次快照不能证明"没有"。

---

## 错误结论 3：归因于 QUIC 被拦 / MTU

`reject udp 443` 排在国内直连规则之前，确实导致国内 QUIC 被误伤（这是真问题，已修：规则后置）。但它**不是**卡顿的主因。

MTU 从 9000 降到 1500 后，首字节有改善（四项方向一致），但故障依旧。

→ 两个都是"看起来合理"的改动，但都没解决主诉。**在根因未定位前优化参数，只是把水搅浑。**

---

## 真正定位到的那一刻

在 sing-box 日志里抓到与用户报告**时间窗完全吻合**的 5 秒超时：

```
03:34:09 ~ 03:34:37   dial tcp 119.188.220.215:443  i/o timeout (5.0s)  ×7
03:35:29              dial tcp 183.60.8.150:80      i/o timeout (5.0s)   ← 腾讯/微信服务器
```

**方法上做对的一件事**：把"用户报告的时间"和"日志的时间"对齐比对，而不是只看日志内容。

---

## 顺带确认的（排除项）

| 检查项 | 结论 | 方法 |
|---|---|---|
| 微信是否被代理绕美国 | 否 | netstat 源端口比对（见 [toolbox](toolbox.md)）|
| 微信 IP 是否被误判为非国内 | 全部正确命中 `geoip-cn` | `sing-box rule-set match` |
| sing-box 是否反复重启 | 否，启动 5 次全是我主动重启 | 守护日志 |
| 本地 Wi-Fi 质量 | 优秀（-47dBm / SNR 45dB / 2401Mbps）| `system_profiler SPAirPortDataType` |
| 网络丢包 | 0%（网关/国内目标/微信服务器）| `ping` |
| 节点是否支撑 IPv6 | 否（经代理请求 IPv6 出口返回 IPv4）| `curl -6 -x` |

---

## 教训汇总

1. **空日志 ≠ 没有事件。** 先验证观测手段。
2. **单次快照不能证明"不存在"。** 给足采样窗口。
3. **时间对齐是最便宜的定位手段。** 用户说"几点几分卡"，就去日志里找那一刻。
4. **根因未明时不要改参数。** 会把多个变量搅在一起，之后更难分离。
5. **用户的体感描述是一手数据，优先级高于我的推断。**
