# 06 · GitHub 访问慢（含一次把服务搞断的失误）

**现象**：Chrome 访问 GitHub 极慢。

**结论先说**：配置层面已经是最优，**改不动了** —— 瓶颈是物理距离 + 链路带宽。

---

## 弯路 1：以为解析到了污染 IP

`github.com` 解析到 `172.182.252.133`，而常见 GitHub IP 是 `140.82.x` / `20.205.x`，怀疑被污染。

**验证**：用 Cloudflare DoH（经节点）查询 → 返回同一个 IP；`ipinfo` 显示归属 **AS8075 Microsoft / Phoenix**（GitHub 属微软，走 Azure）。

→ **是真实 IP，怀疑不成立。**

---

## 弯路 2：以为 sing-box 这一层有开销

**方法**：用 `-x socks5h://127.0.0.1:10808` 直连 xray（回环地址不进 TUN），与走 TUN 对比，隔离 sing-box 的影响。

```
经 TUN:        DNS 0.003s  TCP 0.002s  TLS 中位 0.804s
绕过 sing-box: DNS 0.000s  TCP 0.000s  TLS 中位 0.768s
```

→ **差异在噪声范围内，sing-box 不是瓶颈。**

（中途曾测到 4.7-5.0s 的长尾，一度以为找到了问题；重测后消失 —— 那是刚重启 TUN 后的暂态。**别拿暂态当结论。**）

---

## 弯路 3（失误）：切换节点把 GitHub 弄断了

尝试切到 `LA-Hysteria2` 做对比，结果 **GitHub 0/10 全部失败**。

**根因**：该节点用**域名**指定，而：

```
解析 hy2.icthub.top → 需要走代理 → 代理需要先解析这个节点 → 死锁
```

已立即回退到固定 IP 的 LA-Reality 并恢复。

**教训**：动生产路径上的网络配置前，先想清楚回退路径。这次的代价是用户断网数分钟。

---

## 真正的瓶颈

| 事实 | 数据 |
|---|---|
| GitHub **直连不可用** | `HTTP 000`（连接失败），必须走代理 |
| TLS 握手 0.8-1.2s | 中国 → 洛杉矶的往返延迟 × 2~3 |
| 节点吞吐 | 2.1 MB/s |
| 链路裸带宽（4 并发）| 1.55 MB/s |
| **代理路径占比** | **11.6 / 13.0 Mbps ≈ 89%** |

→ 已经吃掉链路绝大部分带宽。剩下的 0.8s 握手延迟是**物理距离**，配置解决不了。

---

## 关键发现：两个节点是同一台服务器

```
LA-Reality    = 216.167.95.77
LA-Hysteria2  = hy2.icthub.top → 解析 = 216.167.95.77    ← 同一个 IP
```

**只是同一台洛杉矶机器的两种协议，换节点不改善任何东西。**

---

## 唯一有效的改善途径

TLS 握手耗时 ≈ 到节点的 RTT × 2~3：

| 节点位置 | 预计 TLS |
|---|---|
| 洛杉矶（当前）| 0.8-1.2s |
| 香港 / 日本 / 新加坡 | ~0.15s |

→ **换亚洲节点可快 3-5 倍。这是订阅侧的事，配置层面无能为力。**

---

## 教训

1. **"慢"要先分成「延迟」和「吞吐」两件事**再查，它们的解法完全不同。
2. **隔离变量要用能绕过问题层的方法**（这里用回环地址绕过 TUN）。
3. **不要拿刚重启后的暂态数据当结论。**
4. **改生产网络前先准备好回退操作**，并在同一个 root 会话里实现（否则回退也要重新授权）。
